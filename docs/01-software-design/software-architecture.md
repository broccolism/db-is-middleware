# 소프트웨어 아키텍처 용어 디버깅

**한 줄로**: 소프트웨어 아키텍처 단원의 모듈화, 추상화, 품질 속성은 "무엇을 밖에서 보는가"와 "무엇을 내부 구조로 만드는가"를 나눠 읽어야 한다.

이 글은 애플리케이션 설계의 소프트웨어 아키텍처 단원을 읽으면서 생긴 질문들을 모은 정리이다.

---

## 📌 3줄 요약

- **시험에선**: 모듈화는 기능 분리, 인터페이스 단순화, 유지보수 용이성을 높이는 설계 기법으로 외운다.
- **이해할 땐**: 전체 기능이 줄어드는 것이 아니라, 각 모듈이 맡는 책임 범위가 명확해져서 모듈 사이 대화가 단순해지는 것이다.
- **주의할 점**: 추상화는 세부사항을 숨기는 것이고, 아키텍처 품질 속성은 시스템의 실행 결과와 내부 구조의 품질을 구분해서 봐야 한다.

---

## 모듈화하면 왜 인터페이스가 단순해질까?

교재 문장:

> 모듈화를 하면 기능의 분리가 가능하고, 인터페이스가 단순해진다.

여기서 "인터페이스가 단순해진다"는 말은 전체 시스템의 기능이 줄어든다는 뜻이 아니다.

더 정확히는 다음에 가깝다.

```text
각 모듈이 맡는 책임 범위가 줄고 명확해져서,
그 모듈과 대화할 때 필요한 정보가 줄어든다.
```

예를 들어 주문 시스템 전체가 하는 일은 꽤 많다.

```text
주문 시스템
├─ 재고 확인
├─ 쿠폰 적용
├─ 결제 승인
├─ 배송 요청
└─ 주문 완료 알림
```

이 모든 일을 한 모듈이 다 맡으면, 호출하는 쪽이 너무 많은 정보를 넘겨야 할 수 있다.

```text
OrderService.processOrder(
  userId,
  items,
  couponCode,
  pointAmount,
  deliveryAddress,
  paymentInfo,
  deliveryOption,
  notificationOption
)
```

반대로 책임을 나누면 각 모듈은 자기 일에 필요한 정보만 받으면 된다.

```text
Inventory.reserve(items)
Coupon.apply(userId, couponCode)
Payment.pay(orderId, paymentInfo)
Delivery.request(orderId, deliveryAddress)
Notification.sendOrderCompleted(userId, orderId)
```

여기서 전체 기능은 줄어들지 않았다. 여전히 주문, 재고, 쿠폰, 결제, 배송, 알림이 모두 존재한다.

달라진 것은 **한 인터페이스가 감당하던 책임이 여러 모듈로 분산된 것**이다.

```text
기능 축소 X
책임 범위 축소 O
전체 기능 유지 O
각 모듈 인터페이스 단순화 O
```

즉 모듈화 덕분에 인터페이스가 단순해진다는 말은 다음처럼 읽으면 안전하다.

```text
잘 모듈화하면 각 모듈의 책임이 명확해지고,
외부에는 필요한 입출력만 드러나므로
모듈 사이 인터페이스가 단순해질 수 있다.
```

다만 모듈화한다고 자동으로 인터페이스가 단순해지는 것은 아니다. 기능을 너무 잘게 쪼개서 호출 순서까지 외부가 모두 알아야 한다면 오히려 인터페이스가 복잡해질 수 있다.

```text
payment.prepare()
payment.validateCard()
payment.requestApproval()
payment.saveApproval()
payment.publishEvent()
```

이 경우는 모듈화는 했지만 내부 절차가 밖으로 새고 있는 것이다. 좋은 모듈은 외부에 이렇게 말하는 쪽에 가깝다.

```text
필요한 정보만 줘. 나머지는 내가 책임질게.
```

## 추상화는 전체를 세분화하는 것일까?

교재 문장:

> 추상화는 문제의 전체적이고 포괄적인 개념을 설계한 후 차례로 세분화하여 구체화시켜 나가는 것이다.

이 문장은 추상화 자체의 정의와 추상화를 활용한 설계 과정을 섞어 말해서 헷갈리기 쉽다.

추상화의 본질은 다음이다.

```text
추상화 = 세부사항을 숨기고 핵심만 드러내는 것
```

예를 들어 `주문 처리`라고 표현하면, 그 안의 재고 확인, 쿠폰 계산, 결제 승인, 배송 요청 같은 세부사항을 잠시 숨긴다. 이게 추상화이다.

```text
주문 처리
```

나중에 이것을 다음처럼 나누는 것은 추상화 자체라기보다 **구체화** 또는 **상세화**이다.

```text
주문 처리
├─ 재고 확인
├─ 쿠폰 적용
├─ 결제 승인
└─ 배송 요청
```

더 내려가면 구현 수준에 가까워진다.

```text
PaymentService.pay(orderId, paymentMethod)
PaymentGateway.requestApproval(...)
PaymentRepository.save(...)
```

따라서 개념을 나누면 이렇게 된다.

| 개념 | 뜻 |
| --- | --- |
| 추상화 | 불필요한 세부사항을 숨기고 핵심만 드러냄 |
| 구체화/상세화 | 숨겨둔 세부사항을 단계적으로 드러냄 |
| 하향식 설계 | 큰 구조에서 작은 구조로 나누며 설계함 |

그러면 교재 문장은 이렇게 번역해서 읽는 편이 낫다.

```text
처음에는 세부사항을 감춘 높은 수준의 개념으로 보고,
설계 과정에서 필요한 만큼 단계적으로 상세화한다.
```

즉 "나중엔 점점 구체화한다"는 말은 추상화의 본질이라기보다, **추상화된 표현에서 출발해 설계를 상세화하는 과정**이다.

```text
추상화 = 숨김
구체화 = 드러냄
설계 과정 = 숨긴 상태에서 시작해서 점점 드러내는 흐름
```

## 소프트웨어 아키텍처 품질 속성의 세 측면은 어떻게 구분할까?

교재에서 소프트웨어 아키텍처의 품질 속성을 시스템 측면, 비즈니스 측면, 아키텍처 측면으로 나누면 일부 하위 속성이 비슷해 보일 수 있다. 이름이 비슷해도 핵심은 **보는 대상**이 다르다는 점이다.

```text
시스템 측면 = 실행 중인 시스템에서 드러나는 품질
비즈니스 측면 = 조직과 사업 목표에서 따지는 품질
아키텍처 측면 = 그 품질을 만들고 바꾸기 쉬운 내부 구조의 품질
```

즉 시스템 측면은 **결과로 드러나는 품질**이고, 아키텍처 측면은 **그 결과를 가능하게 하는 구조의 품질**이다.

| 측면 | 핵심 질문 | 예시 |
| --- | --- | --- |
| 시스템 측면 | 실행되는 시스템이 잘 동작하는가? | 성능, 보안, 가용성, 사용성 |
| 비즈니스 측면 | 사업 목표와 제약에 맞는가? | 비용, 일정, 시장 대응, 조직 적합성 |
| 아키텍처 측면 | 구조가 좋은 품질을 만들고 유지하기 쉬운가? | 변경 용이성, 확장성, 재사용성, 테스트 용이성 |

예를 들어 성능을 보면 차이가 드러난다.

```text
시스템 측면 성능
= 사용자가 요청했을 때 빠르게 응답하는가?
= 초당 요청을 많이 처리하는가?

아키텍처 측면 성능
= 성능 병목을 분리하고 개선하기 쉬운 구조인가?
= 캐시, 비동기 처리, 확장 구조를 넣기 쉬운가?
```

보안도 마찬가지이다.

```text
시스템 측면 보안
= 권한 없는 사용자가 데이터에 접근하지 못하는가?
= 통신과 저장 데이터가 보호되는가?

아키텍처 측면 보안
= 인증/인가 책임이 한곳에 잘 모여 있는가?
= 보안 정책을 바꿀 때 전체 코드를 뒤집지 않아도 되는가?
```

비즈니스 측면은 기술적 품질보다 조직의 목표와 제약에 가깝다.

```text
비즈니스 측면
= 출시 일정에 맞출 수 있는가?
= 개발 비용이 감당 가능한가?
= 시장 변화에 빨리 대응할 수 있는가?
= 기존 조직과 운영 방식에 맞는가?
```

이름이 비슷해서 헷갈릴 때는 다음 질문으로 구분하면 된다.

```text
이 품질은 실행 결과를 말하나?
-> 시스템 측면

이 품질은 사업 목표, 비용, 일정, 조직 제약을 말하나?
-> 비즈니스 측면

이 품질은 구조를 바꾸고 유지하기 쉬운지를 말하나?
-> 아키텍처 측면
```

한 줄로 정리하면 다음과 같다.

```text
시스템 측면 = 사용자/운영자가 겪는 결과
비즈니스 측면 = 조직/사업이 따지는 가치
아키텍처 측면 = 개발자가 다루는 내부 구조
```

## 🎯 정처기 문제 풀 때 꿀팁

**키워드 매칭 전략**:

- `모듈화`, `기능 분리`, `인터페이스 단순화` -> 책임 단위를 나누고 필요한 입출력만 드러냄
- `인터페이스 단순화` -> 전체 기능 축소가 아니라 모듈별 책임 범위 축소
- `추상화` -> 세부사항을 숨기고 핵심 개념만 표현
- `구체화`, `상세화` -> 숨겨둔 세부사항을 단계적으로 드러냄
- `하향식 설계` -> 큰 구조에서 작은 구조로 내려가며 설계
- `시스템 측면 품질` -> 실행 중인 시스템에서 사용자/운영자가 겪는 결과
- `비즈니스 측면 품질` -> 비용, 일정, 시장 대응, 조직 적합성 같은 사업 가치
- `아키텍처 측면 품질` -> 좋은 품질을 만들고 바꾸기 쉬운 내부 구조

**함정 주의**:

- 모듈화한다고 인터페이스가 자동으로 단순해지는 것은 아니다. 책임 경계가 명확해야 단순해진다.
- 모듈화는 전체 기능을 줄이는 것이 아니라, 한 모듈이 감당하던 책임을 나누는 것이다.
- 추상화와 구체화는 반대 방향의 개념이다. 교재 문장은 추상화의 정의와 설계 과정을 한 문장에 섞어 놓은 것으로 읽는다.
- 시스템 측면과 아키텍처 측면의 품질 속성이 비슷해 보여도, 전자는 실행 결과이고 후자는 그 결과를 가능하게 하는 구조이다.
