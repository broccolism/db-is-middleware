# 요구사항 분석 용어 디버깅

**한 줄로**: 구조적 분석, DFD, DD, CASE, HIPO, TAGS는 요즘 실무 용어라기보다 전통적인 소프트웨어 공학 문맥의 분석/문서화 도구에 가깝다.

이 글은 요구사항 분석 단원을 읽으면서 생긴 질문들을 모은 정리이다.

---

## 📌 3줄 요약

- **시험에선**: 구조적 분석은 자료 흐름 중심, DFD는 버블 차트, DD는 자료 정의, CASE는 자동화 도구, HIPO는 계층적 IPO 도식화 기법, UML은 OMT/Booch/OOSE 통합으로 외운다.
- **이해할 땐**: "당연한 말"처럼 보이는 문장은 대부분 예전의 비정형 문서 작성 방식과 대비되는 표현이다.
- **결론**: 이 단원은 현대 실무 용어라기보다 DFD, DD, HIPO 같은 고전적 분석 산출물을 구분하는 문제로 접근하는 편이 낫다.

---

## 구조적 분석은 왜 "자료 흐름과 처리"를 강조할까?

교재 문장:

> 구조적 분석 기법은 자료의 흐름과 처리를 중심으로 하는 요구사항 분석 방법이다.

처음 보면 "시스템이 데이터를 처리하는 건 당연한 말 아닌가?" 싶다. 핵심은 시스템이 데이터를 다룬다는 일반론이 아니라, 분석의 기준을 **자료 흐름과 처리 과정**에 둔다는 점이다.

구조적 분석은 시스템을 대략 이렇게 본다.

```text
입력 자료 -> 처리 과정 -> 출력 자료 또는 저장소
```

즉 질문이 이렇게 바뀐다.

```text
이 데이터는 어디서 와서,
어떤 처리 과정을 거쳐,
어디로 흘러가는가?
```

객체지향 분석과 비교하면 차이가 선명하다.

| 구분 | 구조적 분석 | 객체지향 분석 |
| --- | --- | --- |
| 중심 관점 | 자료 흐름, 처리 과정 | 객체, 클래스, 책임 |
| 핵심 질문 | 데이터가 어떻게 이동하고 처리되는가? | 어떤 객체가 어떤 책임을 가지는가? |
| 대표 산출물 | DFD, DD, 소단위 명세서 | 클래스 다이어그램, 시퀀스 다이어그램 |

---

## ERD는 객체지향 분석 기법일까?

ERD는 객체지향 분석 기법이라기보다 **데이터 중심 모델링 도구**에 가깝다.

ERD는 다음을 본다.

```text
어떤 데이터 개체가 있고,
그 개체들이 어떤 관계를 맺는가?
```

객체지향 분석은 여기에 더해 객체의 행동과 책임을 본다.

```text
Customer.placeOrder()
Order.calculateTotalPrice()
Payment.approve()
```

| 구분 | 개체 Entity | 객체 Object |
| --- | --- | --- |
| 주 사용 맥락 | ERD, 데이터 모델링 | 객체지향 분석/설계 |
| 관심사 | 저장할 데이터와 관계 | 상태, 행동, 책임 |
| 구성 | 속성, 식별자, 관계 | 속성, 메서드, 메시지 |

ERD의 개체는 클래스 후보가 될 수 있다. 하지만 ERD를 객체지향 모델로 그대로 복사하는 것은 아니다. 예를 들어 `주문`과 `상품`의 다대다 관계는 DB에서는 중간 테이블이 되지만, 객체지향에서는 `OrderItem`처럼 의미 있는 객체가 될 수 있다.

---

## 하향식이면 중복이 자동으로 없어질까?

교재 문장:

> 구조적 분석 기법은 하향식 방법을 사용하여 시스템을 세분화할 수 있고, 분석의 중복을 배제할 수 있다.

엄밀히 말하면 하향식이라는 이유만으로 중복이 자동 제거되지는 않는다. 더 정확한 의미는, 큰 기능을 작은 기능으로 단계적으로 나누면 기능 경계가 명확해져서 **중복을 발견하고 줄이기 쉬워진다**는 것이다.

```text
주문 처리 시스템
├─ 주문 접수
├─ 재고 확인
├─ 결제 처리
└─ 배송 요청
```

잘못 나누면 하향식 분석에서도 중복은 생긴다.

```text
회원 관리
├─ 회원 정보 수정
└─ 개인정보 변경

마이페이지
├─ 개인정보 변경
└─ 전화번호 변경
```

시험에서는 "하향식 구조화는 중복 분석을 줄이는 데 유리하다" 정도로 이해하면 된다.

---

## "모든 단계에서 명세서 작성 가능"은 왜 특징일까?

교재 문장:

> 시스템 개발의 모든 단계에서 필요한 명세서 작성이 가능하다.

현대적인 감각으로는 당연한 말처럼 보인다. 여기서의 포인트는 "문서를 쓸 수 있다"가 아니라, 구조적 분석 기법이 **정형화된 산출물을 만들기 좋다**는 뜻이다.

대표 산출물은 다음과 같다.

| 산출물 | 역할 |
| --- | --- |
| DFD | 자료 흐름과 처리 과정 표현 |
| DD | 자료 항목의 의미와 구조 정의 |
| 소단위 명세서 | 처리 절차 상세 설명 |
| ERD | 데이터 개체와 관계 표현 |
| 상태 전이도 | 상태 변화 표현 |

회의록이나 자연어 설명만으로 요구사항을 관리하면 설계, 구현, 테스트 단계에서 기준이 흔들릴 수 있다. 구조적 분석은 DFD, DD, 명세서 같은 산출물을 통해 이 기준을 문서화한다는 점이 장점으로 다뤄진다.

## DFD를 왜 버블 차트라고 부를까?

DFD는 **Data Flow Diagram**, 즉 자료 흐름도이다. DFD를 버블 차트라고도 부르는 이유는 처리 과정을 원형 또는 둥근 기호로 표현하기 때문이다.

| 요소 | 의미 | 표기 |
| --- | --- | --- |
| 처리 Process | 입력 자료를 출력 자료로 변환 | 원, 둥근 사각형 |
| 자료 흐름 Data Flow | 데이터 이동 | 화살표 |
| 자료 저장소 Data Store | 데이터 저장 위치 | 평행선, 열린 사각형 |
| 단말 External Entity | 시스템 외부의 사람/기관/시스템 | 사각형 |

중요한 점은 DFD의 화살표가 명령 순서가 아니라 **자료가 이동하는 방향**을 뜻한다는 것이다. 예를 들어 결제 처리 프로세스가 외부 결제 시스템으로 `결제 요청`을 보내면, 결제 시스템은 다시 `결제 결과`를 돌려준다.

```text
결제 처리 -> 결제 시스템: 결제 요청
결제 시스템 -> 결제 처리: 결제 결과
```

---

## DD는 그냥 표가 아니다

DD는 **Data Dictionary**, 즉 자료 사전이다.

자료 사전은 DFD에 나온 자료 흐름이나 자료 저장소를 더 자세히 정의한다. 다만 핵심은 단순 설명표가 아니라, 약속된 기호로 **자료의 구성식**을 적는다는 점이다.

대표 표기법:

| 기호 | 의미 |
| --- | --- |
| `=` | 정의 |
| `+` | 연결 |
| `{}` | 반복 |
| `[]` | 선택 |
| `()` | 생략 가능 |
| `**` | 주석 |

예를 들어 온라인 주문 시스템의 자료 사전은 다음처럼 쓸 수 있다.

```text
주문 정보 = 고객번호 + {주문상품} + 배송지 + 결제수단
주문상품 = 상품번호 + 주문수량
재고 결과 = 상품번호 + [재고있음 | 품절] + (가능수량)
결제 결과 = 주문번호 + [승인 | 거절] + (승인번호) + (실패사유)
주문 저장 = 주문번호 + 고객번호 + {주문상품} + 총금액 + 주문상태
```

![자료 사전 DD 예시](/img/requirements-analysis/data-dictionary-dd-example.png)

핵심은 DFD에 나온 자료명을 "정확히 어떤 항목으로 구성된 자료인가?"까지 풀어쓴다는 것이다.

## CASE는 무엇의 약자일까?

CASE는 **Computer Aided Software Engineering**의 약자이다. 한국어로는 컴퓨터 지원 소프트웨어 공학 정도로 볼 수 있다.

교재에서 요구사항 분석 CASE를 자동화 도구라고 설명한다면, 다음 작업을 지원하는 도구로 이해하면 된다.

- 요구사항 문서 작성
- DFD, ERD 같은 분석 모델 작성
- 자료 사전 관리
- 모델 간 일관성 검사
- 설계 문서 자동 생성
- 변경 사항 추적

CASE는 1980~1990년대 소프트웨어 공학에서 자주 쓰이던 전통적인 용어이다. 요즘에는 CASE라는 큰 이름보다 요구사항 관리 도구, UML 모델링 도구, 테스트 자동화 도구, ALM 도구, DevOps 도구처럼 더 구체적인 이름을 많이 쓴다.

---

## CASE와 HIPO는 무슨 관계일까?

CASE는 **자동화 도구**이고, HIPO는 **분석/설계 내용을 표현하는 도식화 또는 문서화 기법**이다.

HIPO는 보통 **Hierarchy Input Process Output**의 약자로 설명된다.

- Hierarchy: 기능을 계층적으로 분해한다
- Input: 입력이 무엇인지 본다
- Process: 처리 과정이 무엇인지 본다
- Output: 출력이 무엇인지 본다

관계는 다음처럼 보면 된다.

| 구분 | CASE | HIPO |
| --- | --- | --- |
| 정체 | 자동화 도구 | 표현/문서화 기법 |
| 역할 | 분석과 설계를 컴퓨터로 지원 | 기능 구조와 IPO를 도식화 |
| 비유 | 모델링 도구 | 그 도구로 그리는 설계도 형식 |

온라인 주문 시스템을 HIPO로 보면 다음과 같다.

```text
주문 시스템
├─ 주문 접수
│  ├─ 입력: 주문 정보
│  ├─ 처리: 주문 유효성 검사
│  └─ 출력: 주문번호
├─ 재고 확인
│  ├─ 입력: 상품번호, 수량
│  ├─ 처리: 재고 수량 조회
│  └─ 출력: 재고 가능 여부
└─ 결제 처리
   ├─ 입력: 주문번호, 결제정보
   ├─ 처리: 결제 승인 요청
   └─ 출력: 결제 결과
```

한 줄로 정리하면, CASE는 HIPO 같은 분석/설계 산출물을 작성하고 관리하는 데 쓰일 수 있는 도구이고, HIPO는 요구사항 분석 내용을 표현하는 기법 중 하나이다.

## TAGS와 IORL은 뭘까?

TAGS는 보통 **Technology for Automated Generation of Systems**의 약자로 설명된다. 한국어로는 시스템 자동 생성 기술 정도로 볼 수 있다.

요구사항 분석용 CASE 도구 맥락에서 TAGS는 사용자의 요구사항을 입력받아 분석/설계 산출물 생성을 지원하는 도구로 다뤄진다. 이때 사용하는 언어가 **IORL**이다.

IORL은 **Input Output Requirement Language**의 약자이다. 말 그대로 **입출력 요구사항 언어**이다.

IORL은 요구사항을 다음처럼 본다.

```text
어떤 입력이 들어오고,
어떤 처리 요구가 있으며,
어떤 출력이 나와야 하는가?
```

예를 들어 온라인 주문 시스템은 이렇게 표현할 수 있다.

```text
INPUT   : 고객번호, 상품번호, 주문수량, 배송지
PROCESS : 재고 확인 및 주문 접수
OUTPUT  : 주문번호, 주문상태, 결제요청정보
```

로그인 기능이라면 다음처럼 볼 수 있다.

```text
INPUT   : 회원 아이디, 비밀번호
PROCESS : 회원 인증
OUTPUT  : 로그인 성공 여부, 사용자 권한
```

성적 처리 시스템이라면 다음처럼 볼 수 있다.

```text
INPUT   : 학번, 과목코드, 점수
PROCESS : 총점과 평균 계산, 등급 산출
OUTPUT  : 성적표
```

핵심은 구조적 분석, HIPO, IORL이 모두 전통적인 `입력 -> 처리 -> 출력` 관점과 가까운 냄새를 낸다는 점이다.

## HIPO의 어순은 왜 어색할까?

HIPO는 네 단어를 같은 수준으로 길게 늘어놓은 말이라기보다, **H + IPO**로 끊어 이해하는 편이 좋다.

```text
HIPO = Hierarchy + Input/Process/Output
```

즉 의미는 다음에 가깝다.

```text
Hierarchy (Input - Process - Output)
```

시스템 기능을 계층 구조로 나누고, 각 기능을 IPO 관점으로 설명한다는 뜻이다.

```text
주문 시스템
├─ 주문 접수
│  ├─ Input: 주문 정보
│  ├─ Process: 주문 유효성 검사
│  └─ Output: 주문번호
└─ 결제 처리
   ├─ Input: 주문번호, 결제정보
   ├─ Process: 결제 승인 요청
   └─ Output: 결제 결과
```

시험용으로는 다음처럼 압축하면 된다.

> HIPO = 계층도 + IPO 명세

## UML에서 Rumbaugh, Booch, Jacobson은 외워야 할까?

교재 문장:

> UML은 Rumbaugh(OMT), Booch, Jacobson 등의 객체지향 방법론의 장점을 통합하였다.

시험용으로는 사람 이름을 아주 깊게 알 필요는 없다. 다만 **UML이 여러 객체지향 방법론을 통합해서 만들어졌다**는 맥락과 대표 이름 정도는 키워드로 알아두는 것이 좋다.

가장 자주 묶이는 이름은 다음 셋이다.

| 사람 | 관련 방법론 | 시험용 기억 |
| --- | --- | --- |
| Rumbaugh | OMT | 객체 모델링 기법 |
| Booch | Booch Method | 객체지향 설계 방법론 |
| Jacobson | OOSE | 유스케이스 중심 방법론 |

여기서 **OMT**는 **Object Modeling Technique**의 약자이다. 한국어로는 객체 모델링 기법 정도로 보면 된다.

Rumbaugh가 자주 나오는 이유는 구조적 분석 쪽의 DFD처럼, 객체지향 분석 쪽에서 OMT가 꽤 대표적인 방법론으로 다뤄졌기 때문이다. OMT는 시스템을 객체 관점으로 모델링하기 위해 다음 세 모델을 강조한다.

| OMT 모델 | 관심사 |
| --- | --- |
| Object Model | 객체, 클래스, 속성, 관계 |
| Dynamic Model | 상태 변화, 이벤트 |
| Functional Model | 자료 흐름, 처리 |

여기서 재미있는 점은 OMT에도 Functional Model이 있어 DFD 같은 자료 흐름 관점이 일부 들어온다는 것이다. 그래서 Rumbaugh는 객체지향 분석 단원에서도, 구조적 분석과 비교할 때도 자꾸 얼굴을 비춘다.

사람 이름 암기 강도는 이렇게 잡으면 된다.

```text
필수: UML은 객체지향 방법론을 통합한 표준 모델링 언어
권장: Rumbaugh = OMT, Booch = Booch, Jacobson = OOSE/Use Case
깊은 암기 불필요: 각 인물의 생애나 세부 표기법 역사
```

한 줄로 정리하면, **UML은 Rumbaugh의 OMT, Booch 방법론, Jacobson의 OOSE 같은 객체지향 방법론을 통합한 표준 모델링 언어**이다.

## 유스케이스는 구조 사물일까, 다이어그램일까?

UML의 사물 분류를 볼 때 특히 헷갈리는 부분이 유스케이스이다.

교재에서는 유스케이스를 구조 사물의 예로 들기도 하고, 다른 곳에서는 유스케이스 다이어그램을 행위 다이어그램으로 분류하기도 한다. 처음 보면 일관성이 없어 보인다.

핵심은 **유스케이스 사물**과 **유스케이스 다이어그램**을 구분하는 것이다.

| 표현 | 정체 | 분류 |
| --- | --- | --- |
| 유스케이스 | 다이어그램 안에 들어가는 타원형 모델 요소 | 구조 사물 |
| 유스케이스 다이어그램 | 액터, 유스케이스, 관계를 모아 만든 그림 | 행위 다이어그램 |

예를 들어 다음 타원 하나는 유스케이스 사물이다.

```text
(상품 주문)
```

하지만 다음 전체 그림은 유스케이스 다이어그램이다.

```text
고객 ---- (상품 주문)
고객 ---- (결제하기)
```

클래스와 클래스 다이어그램을 나눠 생각하는 것과 비슷하다.

| 요소 | 다이어그램 |
| --- | --- |
| 클래스 | 클래스 다이어그램 |
| 객체 | 객체 다이어그램 |
| 컴포넌트 | 컴포넌트 다이어그램 |
| 유스케이스 | 유스케이스 다이어그램 |

유스케이스가 의미상으로는 사용자의 행위나 시스템 기능을 나타내기 때문에 행동 사물처럼 느껴질 수 있다. 하지만 UML 사물 분류에서는 시스템이 제공하는 기능 단위를 나타내는 정적인 모델 요소로 취급해 구조 사물로 분류한다.

시험용으로는 이렇게 잡으면 된다.

> 유스케이스 사물은 구조 사물, 유스케이스 다이어그램은 행위 다이어그램.

## 🎯 정처기 문제 풀 때 꿀팁

**키워드 매칭 전략**:

- `자료 흐름`, `처리 중심`, `하향식` -> 구조적 분석
- `버블 차트`, `자료 흐름`, `처리`, `저장소`, `단말` -> DFD
- `=`, `+`, `{}`, `[]`, `()` -> 자료 사전 DD
- `Computer Aided Software Engineering`, `자동화 도구` -> CASE
- `Hierarchy Input Process Output`, `계층도`, `입력-처리-출력` -> HIPO
- `Technology for Automated Generation of Systems`, `IORL` -> TAGS
- `Input Output Requirement Language`, `입출력 요구사항 언어` -> IORL
- `Rumbaugh`, `Booch`, `Jacobson`, `OMT`, `OOSE` -> UML의 객체지향 방법론 통합 배경
- `유스케이스 사물` -> 구조 사물
- `유스케이스 다이어그램` -> 행위 다이어그램

**함정 주의**:

- ERD는 객체지향 분석 기법의 대표 도구라기보다 데이터 중심 모델링 도구로 보는 것이 안전하다.
- DD를 단순 용어 설명표로만 이해하면 부족하다. 시험에서는 DD 표기 기호를 함께 묻기 쉽다.
- CASE는 요즘 실무에서 자주 쓰는 말은 아니지만, 전통적인 소프트웨어 공학 용어로 시험에 남아 있다.
- HIPO는 `Hierarchy + IPO`로 끊어 이해하면 어순이 덜 이상하다.
- 사람 이름은 세부 역사보다 `Rumbaugh = OMT`, `Booch`, `Jacobson = OOSE/Use Case` 연결만 우선 잡는다.
- 유스케이스는 문맥에 따라 "사물"일 수도 있고 "다이어그램"일 수도 있다. 둘을 섞으면 분류가 꼬인다.
