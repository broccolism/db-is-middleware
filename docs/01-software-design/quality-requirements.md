# 품질 요구사항 용어 디버깅

**한 줄로**: 품질 요구사항 단원의 ISO/IEC 9126과 25010은 소프트웨어를 어떤 관점으로 평가할지 정리한 품질 모델이다.

이 글은 품질 요구사항 단원에서 헷갈린 표준 이름, 품질 특성 분류, 번역어를 따로 모은 정리이다.

---

## 📌 3줄 요약

- **시험에선**: ISO/IEC 9126은 6개 품질 특성, ISO/IEC 25010은 8개 품질 특성으로 외운다.
- **이해할 땐**: 25010은 9126을 완전히 갈아엎은 것이 아니라, 보안성과 호환성을 상위 특성으로 끌어올린 재배치에 가깝다.
- **주의할 점**: 준수성은 기능의 규칙 준수, 안정성은 변경 후 부작용, 운용성과 친밀성은 사용자 관점으로 이해한다.

---

## ISO/IEC 9126에서 ISO/IEC는 왜 같이 붙을까?

ISO/IEC 9126은 소프트웨어 품질을 평가하기 위한 국제 표준이다. 이름의 앞부분은 다음처럼 보면 된다.

| 약자 | 뜻 | 역할 |
| --- | --- | --- |
| ISO | International Organization for Standardization | 산업 전반의 국제 표준화 기구 |
| IEC | International Electrotechnical Commission | 전기·전자·전기기술 국제 표준화 기구 |

둘이 같이 붙는 이유는 정보기술 표준을 위해 **ISO/IEC JTC 1**이라는 합동 기술위원회가 만들어졌기 때문이다.

```text
ISO/IEC JTC 1 = 정보기술 표준화 합동 기술위원회
ISO/IEC JTC 1/SC 7 = 소프트웨어와 시스템 공학 담당 분과
```

즉 ISO/IEC 9126은 "ISO와 IEC가 갑자기 같이 만든 이상한 표준"이 아니라, 컴퓨터와 소프트웨어가 산업 표준과 전기전자 표준의 경계에 걸쳐 있기 때문에 **정보기술 영역을 공동으로 다루는 구조**에서 나온 표준이다.

IEEE가 아무것도 하지 않은 것은 아니다. IEEE는 전기전자·컴퓨터 분야의 전문가 협회 기반 표준화 조직이고, IEEE 802 같은 유명한 표준도 만들었다. 소프트웨어 공학 표준에서도 IEEE는 독자 표준을 만들거나 ISO/IEC와 협력한다. 그래서 어떤 표준은 `ISO/IEC/IEEE 12207`처럼 세 이름이 함께 붙기도 한다.

시험용 감각은 이렇게 잡으면 된다.

```text
ISO/IEC 9126
= ISO와 IEC의 정보기술 합동위원회 JTC 1,
  그중 소프트웨어/시스템 공학 담당 SC 7 쪽 표준
```

## ISO/IEC 9126에서 준수성은 왜 기능성 하위일까?

여기서 준수성은 품질 전체가 표준을 잘 지키는지를 넓게 말하는 것이 아니라, **기능이 관련 표준, 법규, 업무 규칙, 계약 조건을 지키며 제공되는가**를 보는 것이다.

예를 들어 결제 기능을 생각해보면 다음처럼 나뉜다.

```text
결제 기능이 있다
-> 기능성 있음

결제 기능이 카드사/PG사 규격대로 승인 요청을 보낸다
-> 기능성의 준수성 있음
```

그래서 ISO/IEC 9126에서 준수성은 기능성 하위 특성으로 놓인다. "기능이 있느냐"뿐 아니라 "그 기능이 요구된 규칙에 맞게 동작하느냐"까지 기능성의 일부로 본 것이다.

## 유지보수성의 안정성은 왜 신뢰성 하위가 아닐까?

ISO/IEC 9126에서 **안정성**은 신뢰성 하위가 아니라 유지보수성 하위에 있다. 여기서 안정성은 평소 말하는 "서버가 안정적으로 돌아간다"의 안정성이 아니다.

핵심은 다음에 가깝다.

```text
안정성 = 수정했을 때 예상치 못한 부작용이 얼마나 적은가
```

즉 운영 중 안정성이 아니라 **변경 후 안정성**이다.

예를 들어 상품 가격 계산 로직을 고쳤는데 배송비 계산, 쿠폰 적용, 주문 취소까지 같이 깨진다면 유지보수성 관점의 안정성이 낮다. 반대로 가격 계산 로직을 수정해도 관련 없는 기능에 영향이 거의 없다면 안정성이 높다.

| 구분 | 핵심 질문 | 가까운 품질 특성 |
| --- | --- | --- |
| 실행 중 잘 버티나? | 장애 없이 계속 동작하는가? | 신뢰성 |
| 고쳤을 때 덜 깨지나? | 수정 후 부작용이 적은가? | 유지보수성의 안정성 |

시험용으로는 이렇게 나누면 된다.

```text
신뢰성 = 실행 중 고장 없이 믿고 쓸 수 있는가
유지보수성의 안정성 = 변경해도 예상치 못한 영향이 적은가
```

## ISO/IEC 25010은 9126에서 어떻게 바뀌었을까?

ISO/IEC 25010:2011에서는 제품 품질 상위 특성이 6개에서 8개로 늘었다. 완전히 새로 만든 모델이라기보다, ISO/IEC 9126의 품질 특성을 현대 시스템에 맞게 재배치한 것에 가깝다.

| ISO/IEC 25010 상위 특성 | 9126에서의 출처 감각 | 설명 |
| --- | --- | --- |
| 기능 적합성 | 기능성에서 파생 | 기능이 요구를 충족하는가 |
| 성능 효율성 | 효율성에서 파생 | 시간, 자원, 처리 용량이 적절한가 |
| 호환성 | 기능성/이식성 일부에서 독립 | 다른 제품, 시스템, 환경과 같이 잘 맞물리는가 |
| 사용성 | 사용성에서 파생 | 사용자가 이해하고 배우고 조작하기 쉬운가 |
| 신뢰성 | 신뢰성에서 파생 | 고장 없이 동작하고 장애 후 회복 가능한가 |
| 보안성 | 기능성의 보안성에서 독립 | 접근 통제, 기밀성, 무결성 등을 보장하는가 |
| 유지보수성 | 유지보수성에서 파생 | 분석, 수정, 테스트, 재사용이 쉬운가 |
| 이식성 | 이식성에서 파생 | 다른 환경으로 옮기기 쉬운가 |

가장 중요한 변화는 **보안성**과 **호환성**이 상위 특성으로 올라온 것이다.

```text
ISO/IEC 9126 기능성
├─ 적합성
├─ 정확성
├─ 상호 운용성
├─ 보안성
└─ 준수성

ISO/IEC 25010
├─ 기능 적합성
├─ 호환성      <- 상호 운용성 계열이 독립
└─ 보안성      <- 보안성이 독립
```

또한 9126의 이식성 쪽에 있던 **공존성**도 25010에서는 호환성 쪽으로 이해하는 편이 자연스럽다.

```text
ISO/IEC 25010 호환성
├─ 공존성: 같은 환경에서 다른 제품과 자원을 나눠 쓰며 문제없이 공존
└─ 상호 운용성: 다른 시스템과 정보를 교환하고 그 정보를 사용할 수 있음
```

즉 호환성은 새로 하늘에서 떨어진 항목이 아니라, 예전 모델에서 흩어져 있던 **다른 것과 같이 잘 작동하는가** 문제를 따로 묶은 것이다.

## 상호 운용성은 무엇일까?

상호 운용성, 즉 **interoperability**는 다른 시스템과 정보를 주고받고, 그 정보를 제대로 사용할 수 있는 능력이다.

단순히 연결되는 것보다 한 단계 더 강한 말이다.

```text
연결성 = 선이 이어짐
상호 운용성 = 이어진 뒤 의미 있는 일을 같이 함
```

예를 들어 쇼핑몰과 결제 PG 시스템이 연결되어 있다고 해도, 데이터 형식과 의미가 맞지 않으면 상호 운용성이 낮다.

상호 운용성이 좋다는 것은 다음을 포함한다.

- 쇼핑몰이 PG사가 요구하는 형식으로 결제 요청을 보낸다.
- PG사가 보낸 승인/거절 코드를 쇼핑몰이 정확히 해석한다.
- 금액, 통화, 주문번호, 승인번호 같은 데이터 의미가 서로 맞는다.
- 오류 코드도 약속된 방식으로 처리한다.

시험용으로는 이렇게 잡으면 된다.

```text
상호 운용성 = 다른 시스템과 정보를 교환하고 사용할 수 있는 능력
```

ISO/IEC 25010에서는 상호 운용성이 호환성 아래에 들어간다. 이유는 내 시스템 혼자 잘 작동하느냐가 아니라 **다른 시스템과 같이 놓였을 때 잘 맞물리느냐**의 문제이기 때문이다.

## 9126에서 25010으로 바뀐 흐름 요약

마지막으로 변화만 압축하면 다음과 같다.

```text
9126: 기능성, 신뢰성, 사용성, 효율성, 유지보수성, 이식성

25010: 기능 적합성, 성능 효율성, 호환성, 사용성,
       신뢰성, 보안성, 유지보수성, 이식성
```

핵심 변화:

```text
기능성 -> 기능 적합성
효율성 -> 성능 효율성
보안성: 기능성 하위 -> 상위 특성
호환성: 상호 운용성/공존성 계열 -> 상위 특성
나머지는 큰 틀 유지
```

한 줄로 말하면, **ISO/IEC 25010은 ISO/IEC 9126의 6개 품질 특성을 유지하면서, 현대 시스템에서 중요해진 보안성과 호환성을 상위 항목으로 끌어올린 모델**이다.

## 사용성의 운용성은 뭘 운용한다는 뜻일까?

ISO/IEC 9126의 사용성 하위 특성 중 **운용성**은 사용자가 소프트웨어를 실제로 조작하고 제어하기 쉬운지를 말한다. 여기서 운용하는 대상은 서버 운영이나 시스템 관리가 아니라, **사용자가 프로그램을 다루는 행위**이다.

영어로는 보통 **operability**이다. 즉 "운영팀이 시스템을 운영한다"보다 "사용자가 기능을 조작한다"에 더 가깝다.

예를 들어 운용성이 좋은 UI는 다음과 같다.

- 자주 쓰는 기능을 찾기 쉽다.
- 버튼과 메뉴의 의미가 명확하다.
- 입력 실수를 했을 때 수정하기 쉽다.
- 실행 취소, 확인, 취소 같은 조작 흐름이 자연스럽다.
- 사용자가 시스템 상태를 보고 다음 행동을 결정할 수 있다.

반대로 운용성이 낮은 경우는 다음과 같다.

```text
기능은 있음
그런데 어디서 실행하는지 모르겠음
실행하면 되돌리기 어려움
오류가 나도 사용자가 뭘 해야 할지 모르겠음
```

시험용으로는 이렇게 압축하면 된다.

```text
사용성 = 사용자가 이해하고, 배우고, 조작하고, 선호할 수 있는가
운용성 = 사용자가 소프트웨어를 쉽게 조작하고 제어할 수 있는가
```

## 사용성 하위 특성은 개발자 관점일까?

아니다. ISO/IEC 9126의 사용성 하위 특성은 기본적으로 **사용자 관점**이다.

```text
사용자가 이 소프트웨어를 이해하고,
배우고,
조작하고,
좋게 느끼며 쓸 수 있는가?
```

그래서 이해성, 학습성, 운용성, 친밀성은 다음처럼 잡으면 된다.

| 하위 특성 | 영어 감각 | 뜻 |
| --- | --- | --- |
| 이해성 | Understandability | 사용자가 소프트웨어의 목적과 사용 방법을 이해하기 쉬운가 |
| 학습성 | Learnability | 사용자가 사용법을 배우기 쉬운가 |
| 운용성 | Operability | 사용자가 실제로 조작하고 제어하기 쉬운가 |
| 친밀성 | Attractiveness | 사용자가 호감과 매력을 느끼며 쓰고 싶어지는가 |

특히 **친밀성**은 번역이 조금 어색하다. 친구처럼 친하다는 뜻이라기보다, 원래 영어인 **attractiveness**에 가깝다.

```text
친밀성 = 사용자가 소프트웨어를 매력적이고 호감 있게 느끼는 정도
```

예를 들어 화면 배치가 편안하고, 문구가 자연스럽고, 색과 글자 크기가 보기 좋고, 계속 쓰기에 거부감이 적다면 친밀성이 높다고 볼 수 있다.

반대로 개발자 관점의 이해 쉬움은 사용성보다는 유지보수성 쪽에 더 가깝다. 예를 들어 코드 구조를 분석하기 쉬운가, 수정하기 쉬운가 같은 문제는 사용자의 사용성이 아니라 유지보수성의 관심사이다.

## 🎯 정처기 문제 풀 때 꿀팁

**키워드 매칭 전략**:

- `ISO/IEC JTC 1/SC 7` -> 소프트웨어와 시스템 공학 표준
- `ISO/IEC 9126`, `기능성`, `준수성` -> 기능이 표준/법규/규칙을 지키는가
- `ISO/IEC 25010` -> 9126에서 보안성과 호환성이 상위 특성으로 독립
- `상호 운용성`, `interoperability` -> 다른 시스템과 정보를 교환하고 사용할 수 있는가
- `안정성`, `stability` -> 수정 후 예상치 못한 부작용이 적은가
- `사용성`, `이해성`, `학습성`, `운용성`, `친밀성` -> 전부 사용자 관점의 쓰기 쉬움
- `운용성`, `operability` -> 사용자가 소프트웨어를 쉽게 조작하고 제어하는가
- `친밀성`, `attractiveness` -> 사용자가 호감과 매력을 느끼는가

**함정 주의**:

- 준수성은 단어만 보면 품질 전체의 준수처럼 보이지만, ISO/IEC 9126에서는 기능성 하위의 functional compliance로 좁혀서 본다.
- 25010의 호환성은 9126의 상호 운용성/공존성 계열을 상위 특성으로 묶은 것으로 이해하면 된다.
- 25010의 보안성은 9126의 기능성 하위 보안성이 상위 특성으로 승격된 것이다.
- 안정성은 신뢰성의 실행 중 안정성이 아니라 유지보수성의 변경 후 안정성이다.
- 운용성은 운영팀의 시스템 운영이 아니라 사용자의 조작 용이성으로 이해한다.
- 친밀성은 친구처럼 친하다는 뜻이 아니라 attractiveness, 즉 사용자가 호감과 매력을 느끼는 정도로 이해한다.
