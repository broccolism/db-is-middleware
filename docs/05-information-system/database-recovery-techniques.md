# 데이터베이스 회복 기법과 갱신 정책

**한 줄로**: `연기 갱신은 REDO만 가능`, `즉각 갱신은 REDO와 UNDO 모두 가능`이라는 표현은 기능의 가능/불가능이라기보다, 회복 시 실제로 필요한 연산이 무엇인지 말하는 것이다.

## 과목 분류 메모

이 내용은 교재에서는 **5과목. 정보시스템 구축관리** 쪽에 들어간다고 설명될 수 있다. 하지만 필기 기출문제 기준으로는 **3과목. 데이터베이스 구축** 범위에서도 등장한 적이 있다.

따라서 이 사이트에서는 교재 흐름에 맞춰 5과목에 기록하되, 개념 자체는 데이터베이스의 트랜잭션 회복 기법으로 본다.

```text
교재 분류: 5과목 정보시스템 구축관리
개념 성격: 데이터베이스 회복, 트랜잭션 로그, REDO/UNDO
기출 체감: 3과목 데이터베이스 구축에서도 나올 수 있음
```

## REDO와 UNDO

먼저 두 회복 연산의 의미를 분리해야 한다.

| 연산 | 뜻 | 언제 필요한가 |
| --- | --- | --- |
| REDO | 확정된 변경을 다시 적용 | COMMIT된 트랜잭션의 결과가 DB에 덜 반영되었을 때 |
| UNDO | 미확정 변경을 원래대로 되돌림 | COMMIT되지 않은 트랜잭션의 변경이 DB에 이미 반영되었을 때 |

짧게 말하면 다음과 같다.

```text
REDO = 했어야 하는 확정 작업을 다시 한다.
UNDO = 하면 안 되는 미확정 작업을 되돌린다.
```

## 연기 갱신 기법

연기 갱신은 트랜잭션 수행 중에는 실제 데이터베이스를 바로 고치지 않는다. 변경 내용은 로그에 기록해두고, COMMIT 이후에 데이터베이스에 반영한다.

```text
트랜잭션 실행 중: 로그에만 기록
COMMIT 전: DB에는 실제 반영하지 않음
COMMIT 후: 로그를 보고 DB에 반영
```

따라서 COMMIT 전 장애가 발생하면 미완료 트랜잭션이 DB에 남긴 흔적이 없다.

```text
DB에 아직 안 썼다
-> 되돌릴 것도 없다
-> UNDO 불필요
```

반대로 COMMIT 후 장애가 발생하면, 확정된 변경이 DB에 완전히 반영되지 못했을 수 있다. 이때는 로그를 보고 다시 적용해야 한다.

```text
COMMIT은 됐다
하지만 DB 반영이 덜 됐을 수 있다
-> REDO 필요
```

그래서 연기 갱신은 다음처럼 정리한다.

```text
연기 갱신 = 회복 시 REDO만 수행
```

여기서 “UNDO를 못한다”는 말은 기술적으로 되돌리는 능력이 없다는 뜻이 아니다. 애초에 COMMIT 전에는 DB를 건드리지 않으므로 **UNDO할 대상이 생기지 않도록 설계된 것**이다.

## 즉각 갱신 기법

즉각 갱신은 트랜잭션 수행 중에도 변경 내용을 실제 데이터베이스에 반영할 수 있다. 물론 로그도 함께 기록한다.

```text
트랜잭션 실행 중: 로그 기록 + DB 반영 가능
COMMIT 전 변경도 DB에 들어갈 수 있음
```

그래서 장애가 발생하면 두 종류의 트랜잭션을 나누어 처리해야 한다.

| 트랜잭션 상태 | DB 상태 가능성 | 필요한 회복 |
| --- | --- | --- |
| COMMIT됨 | 확정 변경이 DB에 덜 반영되었을 수 있음 | REDO |
| COMMIT 안 됨 | 미확정 변경이 DB에 이미 반영되었을 수 있음 | UNDO |

즉각 갱신에서는 COMMIT 전 변경도 DB에 들어갈 수 있으므로, 장애 시 미완료 트랜잭션의 흔적을 지워야 할 수 있다.

```text
아직 COMMIT 안 됐다
그런데 DB에는 이미 써버렸다
-> UNDO 필요
```

그리고 COMMIT된 트랜잭션은 확정된 결과를 보장해야 하므로 다시 적용할 수 있어야 한다.

```text
COMMIT은 됐다
하지만 DB 반영이 덜 됐을 수 있다
-> REDO 필요
```

그래서 즉각 갱신은 다음처럼 정리한다.

```text
즉각 갱신 = 회복 시 REDO와 UNDO 모두 필요할 수 있음
```

## 교재 문장 다시 읽기

교재에서 다음처럼 말하면 오해가 생긴다.

```text
연기 갱신 기법은 REDO 작업만 가능하다.
즉각 갱신 기법은 REDO와 UNDO 모두 사용 가능하다.
```

이 문장은 마치 어떤 기법이 특정 회복 기능을 기술적으로 지원하거나 지원하지 않는다는 뜻처럼 보인다. 하지만 핵심은 가능 여부가 아니라 **필요 여부**다.

더 정확히는 다음처럼 읽어야 한다.

```text
연기 갱신 기법은 회복 시 REDO만 수행한다.
연기 갱신에서는 COMMIT 전 DB 반영이 없으므로 UNDO 대상이 없다.
```

```text
즉각 갱신 기법은 회복 시 REDO와 UNDO가 모두 필요할 수 있다.
즉각 갱신에서는 COMMIT 전 변경도 DB에 반영될 수 있기 때문이다.
```

## 비교 표

| 기법 | DB 반영 시점 | COMMIT 전 장애 | COMMIT 후 장애 | 회복 연산 |
| --- | --- | --- | --- | --- |
| 연기 갱신 | COMMIT 후 반영 | DB를 안 건드렸으므로 UNDO 대상 없음 | 확정 변경을 다시 적용 | REDO |
| 즉각 갱신 | COMMIT 전에도 반영 가능 | 미확정 변경을 되돌려야 할 수 있음 | 확정 변경을 다시 적용 | UNDO + REDO |

## 시험용 정리

```text
연기 갱신
= COMMIT 전에는 DB에 실제 반영하지 않음
= UNDO할 대상이 없음
= REDO만 수행
```

```text
즉각 갱신
= COMMIT 전에도 DB에 실제 반영 가능
= 미완료 트랜잭션은 UNDO
= 완료 트랜잭션은 REDO
```

최종 감각은 다음이다.

```text
UNDO = 잘못 들어간 미확정 변경 제거
REDO = 확정됐지만 덜 들어간 변경 재적용
```
